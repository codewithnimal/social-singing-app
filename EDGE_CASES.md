# Edge Cases

## Phase 2: Authentication
The following edge cases have been identified and handled during the implementation of the Authentication flow:

1. **Duplicate Account Creation**: Handled. The `POST /register` endpoint returns a `400 Bad Request` if a user attempts to register with an email or username that already exists in the database.
2. **Invalid Credentials**: Handled. The `POST /login` endpoint returns a `401 Unauthorized` if the password does not match the hashed password in the database, or if the user does not exist.
3. **Malformed Credentials**: Handled by FastAPI's built-in Pydantic validation (e.g., invalid email formats return `422 Unprocessable Entity`).
4. **Missing Token**: Handled. Protected endpoints (like `GET /me`) return `401 Unauthorized` without a token.
5. **Expired Token**: Handled. PyJWT raises an `ExpiredSignatureError`, caught by our dependency, returning a `401 Unauthorized`.
6. **Invalid Token**: Handled. Non-parsable or invalidly signed tokens raise a `DecodeError`, caught and mapped to `401 Unauthorized`.
7. **Unauthorized User**: Handled. If a token contains a `sub` that no longer exists in the database, access is rejected.
8. **Accessing another user's private data**: Handled conceptually for this phase by strictly using the `current_user` injected dependency to fetch `me`. Data leakage is prevented because endpoints rely on the server-verified token payload, not client-provided user IDs.

## Phase 3: Friend System
1. **Self Request**: Handled. API returns 400 if `user_id == friend_id`.
2. **Duplicate Request**: Handled. Prevents sending another request if one is already pending or accepted.
3. **Already Accepted/Rejected**: Handled. Users cannot accept/reject a request that is already in that state.
4. **Reverse Request**: Handled. If A sends to B, B cannot send a request back to A; B is told to accept A's request.
5. **Deleted/Nonexistent User**: Handled. Attempting to add a nonexistent `friend_id` returns 404.
6. **Simultaneous Requests**: Handled by application logic checking for existing edges in either direction.
7. **Remove Nonexistent Friendship**: Handled. Trying to delete a friendship that doesn't exist or isn't accepted returns 404.
8. **Unauthorized Request**: Handled globally by the JWT dependency (`get_current_user`).

## Phase 4: 1-to-1 Text Chat
1. **Empty Message**: Handled via Pydantic (`min_length=1`).
2. **Whitespace-only Message**: Handled manually using `.strip()` and returning `400 Bad Request` if empty.
3. **Extremely Long Message**: Handled via Pydantic (`max_length=2000`).
4. **Unauthorized Conversation Access**: Handled. Endpoints explicitly require an *active* friendship state between the current user and the target `friend_id` before querying or creating a `Conversation`. If you are not friends, you cannot access or start a conversation.
5. **Nonexistent Recipient / Invalid ID**: Handled. If the recipient doesn't exist, the friendship query returns nothing, resulting in a `403 Forbidden`.
6. **Messaging Oneself**: Handled. API explicitly rejects this with `400 Bad Request`.
7. **Duplicate Conversation Creation**: Handled. A unique constraint ensures only one conversation per user pair exists. The application guarantees `user1_id < user2_id` when finding or creating.
8. **Correct Chronological Ordering**: Handled. History is queried using `.order_by(desc(Message.created_at))` so the latest messages are fetched first.
9. **Pagination Edge Cases**: Handled. Uses `page` and `size` query params, validating `page >= 1` and `1 <= size <= 100`. Requesting a page beyond the available messages successfully returns an empty array.
10. **Deleted/Removed Friendship**: Handled. If a user deletes a friend, the friendship status is no longer `accepted`. The chat endpoints immediately block sending new messages or fetching history (`403 Forbidden`).
11. **Missing/Expired Token**: Handled securely by the global `get_current_user` dependency.
12. **Network Retry Duplication (Duplicate Send)**: Handled. The `MessageCreate` schema accepts an optional `client_msg_id` (a UUID generated by the client). The server enforces idempotency by checking if this ID exists before inserting. If the client retries the same request due to a network timeout, the server simply returns the existing message without duplicating it in the database.
13. **Out-of-Order Timestamps**: Handled. The server completely ignores any timestamp provided by the client (they are not included in the schema). The server acts as the absolute source of truth for time, stamping messages with `datetime.now(timezone.utc)`. This strictly enforces correct chronological ordering regardless of malicious or out-of-sync client clocks.

## Phase 6: Audio Effects
1. **Missing Recording**: Handled. UI disables effect selection if no original recording URI exists.
2. **Missing File for Processing**: Handled. FFmpeg failure logs are caught in a `try/catch` block, alerting the user and gracefully failing back to the `original` state without crashing.
3. **Repeated Taps**: Handled. Multi-taps are blocked by an `isProcessing` boolean state that disables all buttons until the FFmpeg promise resolves.
4. **Stacked Effects**: Handled. We enforce a "Star Topology" (e.g. `Original -> Kongu`). When an effect is applied, it always uses `originalUri` as the input flag for FFmpeg, never chaining off a previously processed output.
5. **Playback during Processing**: Handled. The Play button is disabled while `isProcessing` is true.
6. **Low Storage / Creation Failure**: Handled natively by FFmpeg Kit returning a non-zero exit code. We catch it via `ReturnCode.isSuccess()`, alert the user, and do not override the playback pointer.

## Phase 7 & 8: Audio Upload & Singing Messages
1. **Send valid audio**: Handled natively.
2. **Send without audio**: Handled. UI disables the "Send" button until a recording and preview are generated.
3. **Cancel before sending**: Handled. Nothing is uploaded until the explicit send action is tapped.
4. **Duplicate Send tap**: Handled. UI state disables the button during upload (`isSending`), and `client_msg_id` enforces idempotency on the backend.
5. **Upload failure / Storage failure**: Handled. Try/catch in React Native captures HTTP errors, resets the UI state, and shows an `Alert` without crashing. On the backend, a database failure triggers a storage deletion rollback.
6. **Network disconnect**: Handled. Axios throws an error caught by the UI try/catch.
7. **Friend removed during send / Receiver blocked**: Handled. Backend checks active friendship state and throws 403 Forbidden.
8. **Invalid MIME type**: Handled. Backend validates the uploaded file content-type.
9. **Fake file extension**: Handled. Backend ensures the actual payload size and type are expected.

## Phase 9: Two-Play Enforcement
1. **First play / Second play**: Allowed natively by updating the `play_count` using atomic SQL `UPDATE`.
2. **Third play**: Handled. Backend atomic query returns 0 rows updated, and the server responds with 403 Forbidden.
3. **Two simultaneous play requests (Concurrency)**: Handled. By using an atomic update (`UPDATE ... WHERE play_count < 2`), even if two requests hit the backend at the exact same millisecond, the database lock ensures only the remaining available plays are consumed. Read-modify-write in Python memory is strictly avoided.
4. **Replay after reinstall / Replay from another device**: Handled. The `play_count` is stored purely server-side on the PostgreSQL row. Client state is untrusted.
5. **Unauthorized user**: Handled. Endpoint verifies the `current_user` is the recipient (or sender, if allowed) of the message.
6. **Invalid message ID / Deleted message**: Handled. Querying nonexistent messages returns 404 Not Found.
7. **Expired audio access**: Handled. If `play_count` hits 2, the endpoint permanently denies the presigned/served URL generation.

## Phase 10: Security Hardening (36/36 tests passing)
1. **alg:none JWT attack**: Handled. PyJWT rejects tokens with `alg: none` by default. Tested and confirmed → 401.
2. **Token for deleted/non-existent user**: Handled. Even with a valid signature, if `sub` doesn't match any user in the DB, access is rejected → 401.
3. **JWT with no `exp` claim**: Fixed. Added `options={"require": ["exp"]}` to `jwt.decode()`. Tokens without expiry are rejected → 401.
4. **Weak JWT secret key**: Fixed. Secret key upgraded from 19-byte `supersecret_dev_key` to 39-byte env-var driven key. Conforms to RFC 7518 minimum of 32 bytes for HS256.
5. **IDOR on message history**: Handled. `get_or_create_conversation()` enforces active friendship before allowing history access. User cannot read another pair's conversation.
6. **IDOR on audio files**: Handled. `serve_audio` validates the requesting user is a member of the conversation extracted from the file path.
7. **Path traversal in audio serve URL**: Handled. FastAPI's path parsing plus the `parts[0] != 'chat_audio'` check blocks `../../../etc/passwd` and URL-encoded variants.
8. **Path traversal in upload filename**: Handled. Storage service generates a UUID-based object key server-side; client filename is never used as a path component.
9. **Oversized upload (11MB)**: Handled. `validate_audio_file()` enforces a 10MB limit → 400/413.
10. **Non-audio file disguised as audio**: Handled. Content-type validation rejects `application/x-php` and similar → 400.
11. **PHP/shell script upload**: Handled. Content-type check in `validate_audio_file()` rejects anything not starting with `audio/` → 400.
12. **SQL injection in effect_id**: Handled. Effect IDs are validated against a whitelist enum (`PRESETS` dict), not interpolated into SQL → 400.
13. **Malformed JSON body**: Handled. FastAPI's Pydantic validation rejects unparseable JSON → 422.
14. **Negative pagination params**: Handled. Query params use `ge=1` constraints → 422.
15. **Oversized pagination (size=999)**: Handled. `le=100` constraint rejects large page sizes → 422.
16. **Stack traces in error responses**: Handled. No `traceback`, `sqlalchemy`, or local file paths appear in any error body tested.
17. **Unauthorized friend request accept/reject**: Handled. `accept` and `reject` endpoints query `WHERE friend_id = current_user.id`, so a user cannot accept a request that wasn't sent to them.
18. **CORS wildcard + credentials**: Acceptable for dev. Production must restrict `allow_origins` to specific domains.
19. **No rate limiting on login**: Known gap. No rate limiting middleware is installed. Acceptable for prototype; production requires a reverse proxy or `slowapi`.
20. **Token expiry**: Tokens now expire after 60 minutes (extended from 30 to avoid frequent re-login during development).
21. **IDOR on effects preview**: Fixed. The preview filename now prepends the `user_id` and `serve_effect_preview` validates that the current user owns the preview file.
22. **Architectural Gaps**: Handled. Added a clean Repository layer for Users, Friends, and Chat domains. Migrated conversations to a `conversation_participants` join table to decouple the strict 1-on-1 logic from the table structure.
