# Audio Concepts

This document maps core audio concepts to how they are implemented and utilized in our mobile social singing application.

## 1. How Microphone Recording Works on Mobile
- **Concept**: A microphone contains a diaphragm that vibrates when struck by sound waves. These mechanical vibrations are converted into an analog electrical signal. The mobile device's built-in ADC (Analog-to-Digital Converter) then samples this continuous analog wave and converts it into discrete digital values (0s and 1s) that the CPU can process and store.
- **Application Context**: Our React Native app requests OS-level permission to access the device's microphone. Once granted, `expo-audio` interfaces with the OS audio APIs (AVAudioRecorder on iOS, AudioRecord on Android) to stream these digital values into a file.

## 2. What an Audio File Is
- **Concept**: An audio file is a digital container that stores the sequence of numbers generated by the ADC, along with metadata (headers) describing how those numbers should be interpreted (e.g., sample rate, bit depth, number of channels).
- **Application Context**: When a user records a singing message, the OS continuously writes the digitized audio data into a temporary file on the device's local storage.

## 3. Audio Format
- **Concept**: The specific encoding and container used to compress and store the audio data. Uncompressed audio (like WAV) is huge. Compressed formats (like MP3, AAC, M4A) use psychoacoustics to remove inaudible frequencies and drastically reduce file size.
- **Application Context**: We will use **M4A (AAC encoding)**. It is highly compressed, offers excellent quality at low bitrates, and is universally supported on both iOS and Android natively, making it perfect for mobile network transmission.

## 4. Sampling Rate
- **Concept**: The number of times per second the analog audio wave is "sampled" (measured). Measured in Hertz (Hz). Higher sampling rates capture higher frequencies.
- **Application Context**: We will use **44,100 Hz (44.1 kHz)**. This is CD-quality standard and captures the full range of human hearing (up to ~22 kHz), which is critical since our app focuses on *singing* where vocal fidelity matters.

## 5. Bitrate
- **Concept**: The amount of data used to represent one second of audio. Higher bitrates mean less compression artifacts and better quality, but larger file sizes.
- **Application Context**: We will use **128 kbps** (kilobits per second). For AAC encoded vocals, 128 kbps is the sweet spot between high-fidelity sound and small file sizes (crucial for fast uploads/downloads).

## 6. File Size Considerations
- **Concept**: File Size (in bits) = Bitrate × Duration.
- **Application Context**: A 10-second singing message at 128 kbps will be approximately 160 Kilobytes (KB). This is tiny. It allows the audio to upload and download almost instantly, preventing latency in the core product loop.

## 7. Local Storage
- **Concept**: The physical flash memory on the mobile device.
- **Application Context**: When the user records, the file is saved to the app's sandboxed temporary cache directory (`FileSystem.cacheDirectory`). Once the message is sent (uploaded) or the user cancels, this local file is deleted to avoid eating up the user's phone storage.

## 8. Playback
- **Concept**: The reverse of recording. The OS reads the digital audio file, decodes the AAC compression, sends the digital samples to the DAC (Digital-to-Analog Converter), which outputs an electrical signal to the device's speaker.
- **Application Context**: The receiver's app downloads the audio file into its local cache and uses `expo-av` to play it. Our business logic wraps the playback function to strictly enforce the "maximum two plays" rule before permanently deleting the local file.
