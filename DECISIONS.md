# Architectural Decisions Record (ADR)

## 1. Storage of Audio Files
- **Decision**: Store audio files in Object Storage (e.g., S3) rather than inside the PostgreSQL database.
- **Rationale**: Audio files are large binary data. Relational databases are optimized for structured data and transactions. Storing audio in PostgreSQL would cause database bloat, slow down backups, and increase database compute costs. Object storage is cheaper, infinitely scalable, and optimized for streaming binary data directly to clients.

## 2. Enforcing the Two-Play Rule
- **Decision**: The two-play rule is enforced exclusively by the backend using a strict database counter.
- **Rationale**: The mobile client is a hostile environment. If the logic were on the client, a user could manipulate the app code, intercept the network request, or reinstall the app to reset local state and replay the audio infinitely. The backend must increment a counter inside a PostgreSQL transaction *before* returning the audio URL.

## 3. Direct Client-to-Storage Uploads (Presigned URLs)
- **Decision**: The mobile client uploads and downloads audio directly from Object Storage using presigned URLs generated by FastAPI.
- **Rationale**: Routing large audio file uploads through the FastAPI server would consume heavy memory and block worker threads. Using presigned URLs offloads the heavy lifting of file transfer to the object storage provider, allowing the FastAPI server to remain lightweight and handle only fast metadata requests.

## 4. Realtime Mechanism
- **Decision**: Use simple WebSockets managed directly within FastAPI for realtime notifications.
- **Rationale**: The project philosophy strictly dictates "Do not over-engineer" and "Do not introduce unnecessary frameworks." While a managed service like Pusher or Firebase would work, FastAPI has native WebSocket support. For a learning project, managing WebSocket connections in memory is the simplest production-like solution.

## 5. Friendship Database Modeling
- **Decision**: Friendships are represented as a single directional row where `user_id` is the requester and `friend_id` is the requestee, instead of a bidirectional pair of rows. Queries to find friends check both columns (e.g. `user_id = me OR friend_id = me`).
- **Rationale**: A single row accurately represents the state of a single edge (pending, accepted, rejected) without synchronization issues that occur when maintaining two reciprocal rows. We use a UniqueConstraint on `(user_id, friend_id)` to prevent multiple duplicate requests in the same direction. Note: There is a theoretical race condition where two users send a request to each other simultaneously, which could create two rows, but this is handled efficiently by application logic rather than complex DB functional constraints to keep the learning implementation simple.

## 6. Local Audio Processing Library (Phase 6)
- **Decision**: Use `react-native-audio-api` (Software Mansion) + pure-JavaScript WAV encoder (`wavEncoder.ts`) for applying voice effects.
- **Rationale**: `ffmpeg-kit-react-native` was investigated first but is officially deprecated and its Maven Central binary (`com.arthenica:ffmpeg-kit-https:6.0-2`) has been removed — all builds fail permanently. `react-native-audio-api` implements the Web Audio API standard on native iOS/Android, is actively maintained, and supports `OfflineAudioContext.startRendering()` which renders the entire processed audio graph in memory as a raw PCM `AudioBuffer`. We then encode that buffer to WAV format using a pure-JS implementation (44-byte RIFF header + 16-bit interleaved PCM). `expo-file-system` (already in the project) writes the WAV base64 blob to the local cache. No paid APIs, no cloud processing. Requires a custom dev build — Expo Go is not supported for this phase because `react-native-audio-api` contains native C++/Kotlin code.
